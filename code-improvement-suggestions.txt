[DUP] 1.1  Eight near-identical input field components
-------------------------------------------------------------------------------
Files:
  src/shared/components/FormFields/AadhaarNumberField.tsx
  src/shared/components/FormFields/EmailField.tsx
  src/shared/components/FormFields/NameField.tsx
  src/shared/components/FormFields/PhoneNumberField.tsx
  src/shared/components/FormFields/GstNumberField.tsx
  src/shared/components/FormFields/PanNumberField.tsx
  src/shared/components/FormFields/UpiIdField.tsx
  src/shared/components/FormFields/IfscCodeFiled.tsx

Issue:
  All eight components follow the exact same structure:
    1. Import FormInput, Input, Label, InputPropTypes, useInputField, useLanguage
    2. Destructure props identically
    3. Call useInputField(props)
    4. Define a handleChange that runs a regex check + length cap, then calls handleInputChange
    5. Render the same FormInput > Label > Input JSX skeleton

  The only differences between them are the regex pattern, max length, and optional
  string transform (e.g., toUpperCase). ~250 lines of near-identical code.

Suggestion:
  Enhance useInputField.ts to accept a validator config:
    { regex?: RegExp; maxLength?: number; transform?: (v: string) => string }
  Then each field component becomes a thin wrapper:
    export const AadhaarNumberField = (props) =>
      <GenericInputField {...props} regex={/^\d*$/} maxLength={12} />;
  This reduces ~250 lines to ~50 and puts all validation logic in one place.

[DUP] 6.1  Eight list/fetch hooks follow the same structure
-------------------------------------------------------------------------------
Files:
  src/shared/features/workers/pages/worker-list/useWorkList.ts
  src/shared/features/users/pages/user-list-page/useUserList.ts
  src/shared/features/clients/pages/client-list/useClientList.ts
  src/shared/features/suppliers/pages/supplier-list/useSupplierList.ts
  src/shared/features/task/pages/task-list/useTaskList.ts
  src/shared/features/report/pages/worker-report/useWorkerReport.ts
  src/shared/features/report/pages/supervisor-attendance-list/useSuperVisorAttendanceList.ts
  src/shared/features/attendance/pages/attendance-list/useAttendanceList.ts

Issue:
  Every hook duplicates the same pattern:
    1. useState for data, loading, searchLoading, error
    2. useEffect on mount to load initial data
    3. A fetch function that builds URLSearchParams and calls the service
    4. A delete handler with confirmation + refresh
    5. A search/filter handler that re-fetches with new params
    6. An applied-filters state + reset handler
  This is ~60-130 lines per hook, all structurally identical.

Suggestion:
  Create a generic useListPage<T> hook (or useListWithFilters<T>) that accepts:
    - fetchFn: (params) => Promise<{ items: T[]; total: number }>
    - deleteFn?: (id) => Promise<void>
    - defaultFilters?: Partial<FilterState>
  Each feature hook then becomes ~10 lines of config wrapping the generic hook.
  This is the highest-impact refactor in the codebase — affects 8 hooks.

-------------------------------------------------------------------------------
Files: All list hooks listed in 6.1

Issue:
  - useWorkList uses: loading + searchLoading + deleteId
  - useAttendanceList uses: loading + paginationLoading
  - useClientList uses: loading only
  - useTaskList uses: loading only
  Different names for the same concept makes it harder to compose or reason about
  loading states across features.

Suggestion:
  Standardize to a single naming convention, e.g.:
    isLoading (initial fetch), isSearching (filter/search re-fetch), isDeleting

[DUP] 7.1  URLSearchParams building is repeated in 28+ service files
-------------------------------------------------------------------------------
Files (sample):
  src/shared/features/attendance/service/AttendanceService.ts     (lines ~18-27)
  src/shared/features/workers/service/WorkerService.ts
  src/shared/features/report/service/WorkerReportService.ts       (lines ~12-23)
  src/shared/features/transaction/service/ClientTransactionService.ts (lines ~17-27)
  src/shared/features/materials/service/PurchaseService.ts        (lines ~17-24)
  src/shared/features/rolesandrights/service/PageService.ts       (lines ~26-34)
  ... and 22+ more files

Issue:
  Every service manually creates a URLSearchParams object and appends params
  inside if/conditional blocks. This boilerplate appears 96+ times across the
  codebase. A single misplaced `if` can silently omit a filter.

Suggestion:
  Create src/shared/utils/buildQueryParams.ts:
    export const buildQueryParams = (params: Record<string, unknown>): string => {
      const q = new URLSearchParams();
      Object.entries(params).forEach(([k, v]) => {
        if (v !== undefined && v !== null && v !== '') q.append(k, String(v));
      });
      return q.toString();
    };
  Replace all manual URLSearchParams blocks with a single call to this utility.

[MAINT] 7.2  Inconsistent service response extraction
-------------------------------------------------------------------------------
Files (sample):
  src/shared/features/users/services/UserService.ts       (line ~21: response.data)
  src/shared/features/task/service/TaskService.ts         (line ~9:  destructured { data })
  src/shared/features/rolesandrights/service/RoleService.ts (line ~25: destructured { data })
  src/shared/features/workers/service/WorkerService.ts    (line ~21: response.data?.items ?? response.data)

Issue:
  Three different patterns for extracting the response body from axios calls.
  Mixed usage makes it unclear which shape to expect, especially in error paths.

Suggestion:
  Pick one pattern and apply it consistently across all services.
  The safest is destructured: `const { data } = await apiClient.get(...)`.

[MAINT] 7.3  Inconsistent service export and naming conventions
-------------------------------------------------------------------------------
Files (sample):
  src/shared/features/rolesandrights/service/PageService.ts    — exports GetPages (PascalCase)
  src/shared/features/materials/service/MaterialService.ts     — exports useMaterialService (hook naming)
  src/shared/features/workers/service/WorkerRoleService.ts     — exports useWorkerRoleService
  src/shared/features/contacts/service/ContactService.ts       — exports { useContactService }

Issue:
  Service functions use three different conventions: PascalCase, camelCase,
  and hook-style (use* prefix). Hook naming (use*) should be reserved for React
  hooks that call useState/useEffect, not plain async service functions.

Suggestion:
  Standardize all service functions to camelCase exports (e.g., getPages, getWorkers).
  Reserve the use* prefix for actual React hooks only.

[MAINT] 7.4  API client error interceptor discards error context
-------------------------------------------------------------------------------
File: src/shared/services/ApiClient.ts  (lines ~17-21)

Issue:
  The response error interceptor just re-throws the raw axios error with no
  transformation. Callers receive inconsistent error shapes (network error vs
  HTTP 4xx vs HTTP 5xx) and each one handles it differently.

Suggestion:
  In the interceptor, normalize errors into a single AppError shape before
  re-throwing, e.g.: { status: number; message: string; code?: string }.
  This lets all catch blocks handle one known type instead of raw AxiosError.
