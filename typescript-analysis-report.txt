               totalPages: number;
               pageNumber: number;
             }

               const { data } = await apiHelper.get(...);
               return data;
             };

─── SVC-04 ──────────────────────────────────────────────────────────────────────
File    : src/shared/services/ApiClient.ts
Issue   : The file exports five separate axios instances (userApiClient,
          masterDataApiClient, siteApiClient, supplierApiClient, workerApiClient)
          but these bypass the token-refresh interceptor defined in ApiHelper.ts.
          Only the _at header is set; no Authorization header and no 401
          interceptor.
Why     : This is an architectural divergence between two patterns:
          (a) useAPIHelper (used by most features) — has full token refresh
          (b) ApiClient.ts instances (used by UserService) — no refresh logic

          the users page, the ApiClient.ts instance will return 401 without
          triggering a refresh.
Recommend: Flag this for architectural review. Either wire ApiClient.ts through
           the same interceptor logic as ApiHelper.ts, or migrate UserService
           to use useAPIHelper.
Priority: High (architectural, not a TS error but a correctness risk)

11. OVERALL TYPESCRIPT QUALITY ASSESSMENT
================================================================================

SUMMARY
───────
The WorkInSite Web project demonstrates a solid TypeScript foundation. The compiler
passes with zero errors under strict mode, the core domain types (DTOs) are
generally well-defined, and patterns like const-enum-with-type (KYCTypes, UpiTypes,
GenderTypes, PaymentMethodEnum) are used correctly throughout. The authentication
helpers, token refresh logic, and API interceptor are well-typed with correct use
of Axios generic types.

The main quality gap is a concentration of 'any' usage (~120 annotations + ~25
casts) that accumulated during a migration from React Native to the web. Many of
these are direct consequences of a few root causes:

  1. Service functions not having explicit return types (causing downstream any
     propagation into components and hooks).
  2. The ComboboxField allItems pattern lacking a type declaration (causing ~20
     'as any' casts at each call-site).
  3. Image fields in purchase/material DTOs typed as 'any' rather than a typed
     array.
  4. Extensive use of catch(error: any) rather than the safer catch(error: unknown)
     combined with the project's existing parseApiError utility.

There are no architectural type errors — the project will not crash due to TypeScript
misconfiguration. The issues are entirely about the precision of the type information
available to developers during editing, which affects how many bugs are caught at
compile-time vs. runtime.

QUALITY RATING: 6.5 / 10

  Strengths:
    + Zero compiler errors with strict mode
    + Good DTO coverage for most domain entities
    + Proper use of 'as const' for enum-like values
    + Correct non-null assertion usage in most places
    + parseApiError and logger utilities are well-typed
    + tokenRefresh.ts and AuthHelper.ts are carefully typed

  Weaknesses:
    - ~120 'any' annotations (roughly 1 per file on average)
    - Service functions return any, losing type guarantees at the call-site
    - Duplicate type definitions (WorkerCategory × 6, WorkerRole × 7)
    - noUnusedLocals and noUnusedParameters are disabled
    - Large blocks of commented-out code in key files

RECOMMENDED NEXT STEPS (in order)

  Step 1 (1–2 days): Fix the ComboboxField allItems type (HIGH-6). This single
    change cascades to remove ~20 'as any' casts with minimal risk.

  Step 2 (2–4 days): Add return type annotations to all service functions (SVC-01).
    Start with the most frequently used services: AttendanceService, WorkerService,
    ContactService, SiteService, MaterialService. This propagates type safety to
    all consumers automatically.

  Step 3 (1 day): Replace all catch(error: any) with catch(error: unknown) +
    parseApiError. The utility is already in place; this is a mechanical change.
    (~54 files, most are single-line changes.)

  Step 4 (0.5 days): Fix the 6 HIGH-priority issues (HIGH-1 through HIGH-5 and
    the Ref pattern) in their individual files.

  Step 5 (1 day): Enable noUnusedLocals and noUnusedParameters in tsconfig.app.json
    and clean up the resulting warnings. This will also trigger removal of the
    commented-out code blocks.

  Step 6 (ongoing): As new features are added, enforce typed service return values
    and avoid any-typed state. The patterns are already in the codebase — they
    just need consistent application.
