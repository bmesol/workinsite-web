================================================================
  useCurrentLocation.ts — Code Explanation
  File: src/shared/hooks/useCurrentLocation.ts
================================================================


OVERVIEW
--------
useCurrentLocation is a custom React hook that provides a single
async function, getLocation(), which:

  1. Asks the browser for the device's GPS coordinates.
  2. Converts those coordinates into a human-readable address via
     reverse geocoding (Google Maps).
  3. Returns an object with three fields: lat, lng, and address.

The full LocationResult type is:

  export type LocationResult = {
    lat: number;
    lng: number;
    address: string;
  };

So the hook is NOT returning only lat/lng — it returns all three
fields. However, in some environments the address field may fall
back to a coordinate string (e.g., "12.9716, 77.5946") instead of
a real street address. The reason for this behaviour is explained
in detail below.


================================================================
STEP-BY-STEP FLOW
================================================================

STEP 1 — Browser Geolocation (requestLocationPermission)
---------------------------------------------------------
The hook calls navigator.geolocation.getCurrentPosition() with:

  - enableHighAccuracy: true   → requests GPS-level precision
  - timeout: 15000             → gives the device 15 seconds
  - maximumAge: 10000          → accepts a cached position up to 10s old

This returns a GeolocationPosition object from the browser. The
hook then destructures it:

  const { latitude, longitude } = position.coords;

These are raw decimal numbers (e.g., 12.9716, 77.5946).

If the user denies location permission  → throws LOCATION_PERMISSION_DENIED
If the browser has no geolocation API   → throws GEOLOCATION_NOT_SUPPORTED
If it times out                         → throws LOCATION_TIMEOUT


STEP 2 — Reverse Geocoding (reverseGeocode)
--------------------------------------------
Reverse geocoding = converting (lat, lng) → a readable address.

The function tries two strategies in order:

  Strategy A — Google Maps JS SDK (window.google.maps.Geocoder)
  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  If the Google Maps JavaScript SDK is already loaded on the page
  (i.e., window.google.maps.Geocoder exists), it uses that first.
  This approach works safely with browser API keys that have
  HTTP-referer restrictions, because the request goes through the
  already-authenticated SDK session rather than a raw HTTP call.

  If it gets a result → returns results[0].formatted_address
  If it fails         → logs a console.warn and falls through to Strategy B

  Strategy B — Geocoding HTTP Endpoint
  ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  Makes a direct HTTP fetch to:
    https://maps.googleapis.com/maps/api/geocode/json?latlng=LAT,LNG&key=API_KEY&language=en

  The API key is read from the environment variable:
    VITE_GOOGLE_MAPS_API_KEY

  If the key is missing (empty string) → logs a warning and immediately
  returns coordsFallback (e.g., "12.9716, 77.5946").

  If the key exists but the API returns a non-OK status (e.g.,
  REQUEST_DENIED, OVER_QUERY_LIMIT, ZERO_RESULTS) → logs the
  status + error_message and returns coordsFallback.

  If the fetch itself throws (network error) → logs and returns coordsFallback.

  coordsFallback is defined as:
    `${lat.toFixed(4)}, ${lng.toFixed(4)}`


WHY THE HOOK APPEARS TO RETURN ONLY LAT/LNG
--------------------------------------------
The hook always returns all three fields (lat, lng, address). But
if any of the following conditions are true, the address field
will contain the coordinate string instead of a real street name:

  1. VITE_GOOGLE_MAPS_API_KEY is not set in the .env file.
     → The key defaults to '' (empty string). Strategy B exits
       immediately and returns "lat, lng".

  2. The API key is set but is restricted to certain HTTP referrers,
     and the Google Maps JS SDK is NOT loaded on the page.
     → Strategy A is skipped (window.google is undefined).
       Strategy B's HTTP request is rejected by Google with
       REQUEST_DENIED, so coordsFallback is returned.

  3. The API key has billing disabled or has exceeded its quota.
     → Google returns OVER_QUERY_LIMIT or similar; coordsFallback
       is returned.

  4. A network error prevents the fetch from completing.
     → The catch block returns coordsFallback.

In all these cases the returned object still has an address field —
it just looks like "12.9716, 77.5946" rather than a street address.
This is an intentional "graceful degradation" design so that
check-in is never blocked even when geocoding fails.


STEP 3 — Return Value
----------------------
getLocation() assembles and returns:

  return {
    lat: latitude,      // raw number from GPS
    lng: longitude,     // raw number from GPS
    address,            // string from geocoding (or coordinate fallback)
  };


================================================================
HOW CALLERS USE THE DATA
================================================================

Two files consume useCurrentLocation:

1. src/shared/components/menu/useSidebarAttendance.ts
   - Calls getLocation() when the supervisor checks in.
   - Passes the entire location object to createSupervisorAttendance
     as the currentLocation field.
   - Also calls setAddress(location.address) to display the address
     in the sidebar UI.

2. src/shared/features/dashboard/supervisor-dashboard/useSupervisorDasboard.ts
   - Calls getLocation() when a site is selected from the picker dialog.
   - Passes all three fields (lat, lng, address) explicitly to
     createSupervisorAttendance:

       currentLocation: {
         lat: location.lat,
         lng: location.lng,
         address: location.address,
       }

So both callers send all three values to the backend API. The
backend stores them under currentLocation on the attendance record.


================================================================
WHY useCallback IS USED
================================================================
The getLocation function is wrapped in useCallback with an empty
dependency array:

  const getLocation = useCallback(async (): Promise<LocationResult> => {
    ...
  }, []);

This makes getLocation referentially stable — the same function
reference is returned on every render. This matters because both
useSidebarAttendance and useSupervisorDasboard list getLocation in
their own useCallback dependency arrays. Without useCallback here,
every render of the component would produce a new getLocation
reference, which would cause those downstream callbacks to also
recreate themselves on every render, potentially triggering
unnecessary re-renders or infinite loops.


================================================================
THE COMMENTED-OUT CODE (Lines 1–63)
================================================================
The top of the file contains an older version of the hook that was
commented out. Compared to the active version, it was simpler:

  - It had no useCallback wrapper.
  - reverseGeocode only tried the HTTP endpoint (no JS SDK Strategy A).
  - It had no TIMEOUT error handling.
  - It returned `${lat}, ${lng}` as the fallback (no toFixed(4)).
  - The console.warn messages were absent.

The active code is a refined, production-ready version of that
original implementation.


================================================================
SUMMARY
================================================================
The hook returns lat, lng, AND address. If it appears to return
only coordinates, the most likely cause is that VITE_GOOGLE_MAPS_API_KEY
is missing or invalid. Check the browser console for the warning:

  [useCurrentLocation] VITE_GOOGLE_MAPS_API_KEY is empty — address
  will fall back to coordinates. Add it to your .env and restart
  the dev server.

Or look for:

  [useCurrentLocation] Geocoding failed — status: REQUEST_DENIED

These messages pinpoint exactly why the address field contains
coordinates instead of a real street name.
