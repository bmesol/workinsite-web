================================================================================
AUTH TOKEN & REFRESH TOKEN — IMPLEMENTATION EXPLANATION
WorkInSite Web Project
================================================================================

OVERVIEW
--------
The application uses JWT (JSON Web Token) based authentication with two tokens:
  1. Access Token  — short-lived, used to authorize every API request
  2. Refresh Token — longer-lived, used to obtain a new access token when the
                     access token expires

Both tokens are generated entirely on the backend. The frontend only stores,
sends, and reacts to them.

================================================================================
1. HOW THE AUTH TOKEN IS GENERATED
================================================================================

File: src/shared/features/auth/services/AuthService.ts (lines 45–62)

The frontend does NOT generate the access token. It calls the backend login
endpoint and receives the token in the response.

  Flow:
    1. User enters phone number and PIN in the sign-in form.
    2. The frontend sends a POST request to:
         POST /auth/login
         Body: { phone: <phoneNumber>, password: <pin> }
    3. The backend validates the credentials and responds with:
         { accessToken: "...", refreshToken: "..." }
    4. Both tokens are extracted from the response and stored (see section 3).

The access token is a JWT. Its expiry, signing algorithm, and payload claims
(Name, UserId, role) are all determined by the backend at the time of login.

================================================================================
2. HOW THE REFRESH TOKEN IS GENERATED
================================================================================

File: src/shared/features/auth/services/AuthService.ts (lines 64–75)

Like the access token, the refresh token is generated entirely by the backend.
The frontend receives it alongside the access token at login.

When the access token expires (the frontend receives a 401 error from any API),
the frontend automatically calls:

    POST /auth/refresh
    Body: { refreshToken: <current refresh token from localStorage> }

The backend validates the refresh token and responds with a brand-new pair:
    { accessToken: "...", refreshToken: "..." }

This is a "refresh token rotation" pattern — every successful refresh gives
the frontend a new refresh token, replacing the old one. The old refresh token
becomes invalid after use.

================================================================================
3. HOW BOTH TOKENS ARE STORED AND USED
================================================================================

STORAGE
-------
File: src/shared/features/auth/helpers/AuthHelper.ts (lines 126–197)

Both tokens are stored in the browser's localStorage using fixed key names:

  Key for access token:   "_at"       (localStorage["_at"])
  Key for refresh token:  "_rt"       (localStorage["_rt"])
  Key for user profile:   "userProfile" (localStorage["userProfile"])

When setAccessToken() is called:
  - The JWT is saved to localStorage["_at"]
  - The token is decoded using the jwt-decode library
  - The decoded payload (Name, UserId, role) is used to build a user profile
    object and saved to localStorage["userProfile"]
  - If the JWT decode fails for any reason, logout() is immediately called

When setRefreshToken() is called:
  - The token is saved directly to localStorage["_rt"] — no decoding

HOW THEY ARE USED
-----------------
File: src/shared/helpers/ApiHelper.ts (lines 141–150)

On every outgoing API request, a request interceptor reads the access token
from localStorage and attaches it to the request headers:

    Authorization: Bearer <accessToken>
    _at: <accessToken>

Both headers are sent for backend compatibility.

The refresh token is never sent on normal API requests. It is only sent to
the /auth/refresh endpoint when a 401 response is received.

AUTHENTICATION CHECK (Route Guard)
-----------------------------------
File: src/shared/components/routehandlers/PrivateRoute.tsx (lines 18–30)

Before rendering any protected page, the PrivateRoute component calls:
    AuthHelper.isAuthenticated()

This function simply checks whether localStorage["_at"] is non-null. It does
NOT check if the JWT is expired — it only checks if the key exists. If the
token is absent, the user is redirected to the sign-in page ("/").

================================================================================
4. HOW TOKEN EXPIRATION IS CURRENTLY HANDLED
================================================================================

File: src/shared/helpers/ApiHelper.ts (lines 152–201)

Token expiration is handled REACTIVELY, not proactively. There is no timer,
setInterval, or scheduled check that monitors when a token is about to expire.
Instead, expiration is detected only when the backend rejects a request.

The full flow when a token expires:

  Step 1: The user makes an action that triggers an API call.
  Step 2: The access token has expired. The backend returns HTTP 401.
  Step 3: The response interceptor in ApiHelper catches the 401.
  Step 4: The interceptor checks if the failing URL is "/auth/refresh" or
          "/auth/login". If it is, calling forceLogout() immediately — there
          is no point trying to refresh if the refresh endpoint itself fails.
  Step 5: If the URL is a regular endpoint, the interceptor checks a global
          flag called "isRefreshing". If a refresh is already in progress,
          the current request is added to a pending queue (pendingQueue[]).
  Step 6: If no refresh is in progress, "isRefreshing" is set to true and
          the interceptor calls AuthService.refreshAccessToken() with the
          refresh token from localStorage.
  Step 7: On success — the new access token and refresh token are stored in
          localStorage, all queued requests are retried with the new access
          token, and the original failed request is also retried.
  Step 8: On failure — all queued requests are rejected, and forceLogout()
          is called, clearing all tokens and redirecting to "/".

The pending queue mechanism (lines 105–116) ensures that if multiple requests
fail simultaneously while the token is expired, only ONE refresh call is made.
All other requests wait in the queue and are replayed once the refresh succeeds.

================================================================================
5. WHY THE USER IS GETTING LOGGED OUT AFTER ~10 MINUTES
================================================================================

The frontend code does NOT set any logout timers or inactivity monitors.
There is no setTimeout, setInterval, or idle-detection code anywhere in the
application. The 10-minute logout is NOT caused by the frontend.

The cause is the BACKEND token configuration.

Here is what is happening:

  a) The backend issues an access token that expires in ~10 minutes.

  b) The backend may also be issuing a refresh token that expires in the same
     ~10 minutes, OR the backend's /auth/refresh endpoint is rejecting the
     refresh token when the access token's session becomes "stale."

  c) When the user is inactive for 10 minutes and then tries to do something:
       - Their access token has expired.
       - The frontend correctly catches the 401 and tries to call /auth/refresh.
       - /auth/refresh also returns 401 (because the refresh token has expired
         or been invalidated by the backend).
       - The interceptor at line 160 detects the 401 on the /auth/refresh URL.
       - forceLogout() is called immediately.
       - The user is logged out.

  This is the chain of events:
    API call → 401 (access token expired) → POST /auth/refresh → 401 (refresh
    token also expired or invalid) → forceLogout() → localStorage cleared →
    redirect to "/"

WHY THE EXPECTED BEHAVIOR (1 WEEK) IS NOT HAPPENING
----------------------------------------------------
The frontend refresh logic is already written correctly to support long-lived
sessions. The code is designed to silently refresh the access token whenever
it expires, as long as the refresh token is still valid.

For a 1-week session to work, the backend must be configured so that:
  - The refresh token has a TTL (time-to-live) of at least 7 days.
  - The /auth/refresh endpoint accepts and honors refresh tokens that were
    issued up to 7 days ago.
  - The backend does NOT invalidate the refresh token based on inactivity.

Currently, neither condition is met — the backend appears to be expiring or
invalidating the refresh token after ~10 minutes.

The fix is entirely on the backend side: extend the refresh token TTL to 7 days.
No frontend code changes are required.

================================================================================
6. WHERE THE LOGOUT / EXPIRATION LOGIC IS HANDLED
================================================================================

There are only four places in the codebase where a user can be logged out:

  A) MANUAL LOGOUT (user clicks logout button)
     File: src/shared/components/menu/Sidebar.tsx
     The sidebar contains a logout button. When clicked, it calls
     AuthHelper.logout() directly.

  B) JWT DECODE FAILURE (corrupt or tampered token)
     File: src/shared/features/auth/helpers/AuthHelper.ts (line 154–157)
     Inside setAccessToken(), if jwtDecode() throws an error (malformed token),
     AuthHelper.logout() is called immediately.

  C) REFRESH TOKEN FAILURE (primary logout path for expired sessions)
     File: src/shared/helpers/ApiHelper.ts (lines 160–163 and 190–193)
     Two triggers:
       - A 401 response on the /auth/refresh or /auth/login endpoint calls
         forceLogout() (lines 160–163).
       - Any error thrown during the refresh attempt (network error, 500, etc.)
         also calls forceLogout() (lines 190–193).

  D) NO REFRESH TOKEN IN STORAGE
     File: src/shared/helpers/ApiHelper.ts (lines 177–180)
     If the access token expires and there is no refresh token in localStorage,
     an Error is thrown, caught immediately, and forceLogout() is called.

WHAT AuthHelper.logout() DOES
------------------------------
File: src/shared/features/auth/helpers/AuthHelper.ts (lines 191–196)

    localStorage.removeItem("_at");       // clears access token
    localStorage.removeItem("_rt");       // clears refresh token
    localStorage.removeItem("userProfile"); // clears user profile
    window.location.href = "/";           // hard-redirects to login page

This is a full session wipe. After this, isAuthenticated() returns false,
and the PrivateRoute redirects the user to the sign-in page.
